## Iteration 12 — PS-12 — 2026-11-05
### The MCP specification, read 2026-11-05 at modelcontextprotocol.io
- specification/versioning: the current revision is 2026-07-28. It has no initialize
  handshake: every request carries its version in `_meta["io.modelcontextprotocol/protocolVersion"]`,
  an unsupported version is error -32022 with data { supported, requested }, and servers
  MUST implement `server/discover`. Revisions 2025-11-25 and earlier are "legacy"
  (initialize-based); a "dual-era" server MAY serve both, choosing per client by how it opens.
- specification/2025-06-18/basic/lifecycle: initialize → { protocolVersion, capabilities,
  serverInfo }; answer the client's version when supported, else the server's latest; the
  example error names 2024-11-05 as a supported version.
- specification/2026-07-28 tools, resources, stdio, server/discover: results carry
  resultType "complete"; tool execution errors are isError: true; an unknown tool and a
  missing resource are -32602; stdout carries MCP messages only; exit on stdin end.
### Decision taken here (reported to the operator in the PR, not an ARC-060 change)
- ARC-060 decision 5 lists initialize, ping, tools/list, tools/call, resources/list and
  resources/read, written against the handshake revisions. A server speaking only those
  would fail every client on the current revision. The server is therefore dual-era: legacy
  versions 2025-11-25, 2025-06-18, 2024-11-05 through initialize, and 2026-07-28 through
  per-request `_meta` plus server/discover. Same two tools, same two resources, same
  descriptor; nothing beyond decision 5's surface is offered (no prompts, no
  subscriptions/listen, no sampling).
- Naming impact: `arcane-presence` (serverInfo.name) appears nowhere else in the repository
  except the architecture and the story that name it; npm has no package of that name
  (`npm view arcane-presence` → 404). It is one more label for the Naming Test.
### What to watch for
- Which revision each client speaks today was not tested against real clients (Claude Code,
  Copilot, Codex): PS-16's registration examples are the place to note it.

## Iteration 19 — a signal race in serve — 2026-11-05
### What happened
- CI run 42016564388 (ubuntu, the review-fix push) failed one test: presence-lifecycle's
  "--rotate replaces the token" saw `serve` exit by signal (exit code null) instead of 0 on
  SIGTERM. Cause: runPresenceServe printed the "listening" line and only then installed its
  SIGINT/SIGTERM listeners. The test waits for that line and signals at once; a signal that
  arrives before Node has a listener takes the default action and kills the process, so
  server.json was left behind.
- Fix: the listeners are installed first, before startPresenceService; a signal that arrives
  before the service is ready is remembered and stops it as soon as it is ready.
### Honest note on the regression test
- The added test ("a SIGTERM that arrives as soon as server.json exists...") passes against the
  fix and, three times out of three, against the old code too: the window is microseconds and a
  2 ms poll does not land in it here. It states the requirement; it does not reproduce the race.
  The evidence for the fix is the cause above and the lifecycle suites passing 3/3 locally.
