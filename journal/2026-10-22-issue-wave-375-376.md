### Lessons Learned

#### An issue's command claims need the same check as any other source

The first draft of the runtime audit followed #376's wording: `eas update:list --branch <channel>` "shows
every runtime that still has phones on it". The eas-cli source shows that command has no device data,
lists only the newest 25 update groups unless told otherwise, and cannot list a runtime that never
received an update. The review rated it HIGH: run as written, the MR-15 gate would report nothing stranded
while phones were stranded, the silent failure the section exists to stop. The first fix, a page of
`eas build:list`, had the same newest-first blind spot (50 builds at most, TestFlight builds among them),
which the second pass caught. The inventory now starts from each store console's release history. Read
the tool's source for every command a spell will tell an agent to run, including the commands the issue
itself quotes, and ask what a command cannot see as well as what it shows.

#### A reviewer's suggestion is a claim too

The second review pass withdrew one of its own first-pass suggestions: R11 had proposed "read the
response's `Cache-Control`", but `max-age` bounds how long a response may be cached, not how old its data
is, so the reader has nothing to decide with. I had applied it as written. Check a review fix the way you
would check your own text before it ships.

#### Running the routine changed its text twice before it shipped

Written from the issue alone, step 4a would have said that a page opened from disk renders with the wrong
character set, and would have quoted Chromium's policy message as "Refused to …". Running it on the
sign-in pages, with controls, showed Chromium decoding an undeclared-charset UTF-8 page correctly from
`file://` and as windows-1252 only over HTTP without a charset, and logging "… violates the following
Content Security Policy directive …". The step now serves the page with production's own headers, checks
the declared charset, and quotes no message. A routine shipped as instructions should be run once, with a
control that proves each check can fail, before it ships.

#### The pull-request body cannot live in `<git-dir>` from a desktop worktree session

`spell-create-pull-request` Step 4 and `spell-commit-work` 9a2 write the body to
`<git-dir>/arcane-pr-body.md`. From this session's linked worktree, `<git-dir>` is the primary checkout's
`.git/worktrees/<name>/`, and the harness refused the write as "in the base repo checkout"; the path it
suggested does not exist, because a worktree's `.git` is a file. The body went to the session scratchpad
with the same first-line branch marker and read back byte-identical after `gh pr create`. The spells'
location rule assumes the agent may write inside `.git`, and names no fallback.
