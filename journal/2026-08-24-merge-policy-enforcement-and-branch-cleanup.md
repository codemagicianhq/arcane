### Lessons Learned

#### A platform can have two independent protection systems, and checking one says nothing about the other

Asked whether `main` had branch protection, the check that came to mind first — GitHub's classic `/branches/{branch}/protection` endpoint — returned a clean, confident "not protected." That was reported as fact. It was wrong. GitHub Rulesets are a separate, newer system with their own API surface, and a repo can be strongly protected through one while showing nothing on the other. The operator caught this by naming the exact ruleset URL from memory; nothing in the check itself would have surfaced it. The generalizable failure isn't "picked the wrong endpoint" — it's asserting a negative ("no protection exists") from checking one of two systems, when the very existence of a second system was knowable in advance from general platform knowledge, not just hindsight.

#### A ruleset's rules aren't independent, and a single field can be right while the rule set is still wrong

Once the right object was found, fixing it took two passes, not one. Changing `allowed_merge_methods` to include `"merge"` looked sufficient on its face — until noticing `required_linear_history` was also active, and that rule unconditionally blocks any merge commit regardless of what the merge-methods list permits. Two rules, individually reasonable, jointly self-defeating: exactly the same *shape* of bug as the sanctioned-strategy-versus-cleanup-tooling conflict this repo's own 2026-08-21 journal entry already named ("a sanctioned strategy can structurally defeat sanctioned tooling") — except this time both halves of the contradiction lived inside the same ruleset object, not across two different docs. Reading a config's field list is not the same as reading its *effective* behavior.

#### The same branch-hygiene mistake recurred immediately after being corrected once

After PR #73 merged, a fresh branch was correctly cut from `origin/main` before starting the next chunk of work. After PR #74 merged, the exact same situation arose — and this time the mistake was made: continuing to commit on the now-merged, now-remote-deleted branch instead of cutting a new one. It surfaced as a genuine "PR branch is behind origin/main" CI failure later, from an unrelated commit landing on `main` in between (someone else's PR #78), and was fixed the same way the field's own 2026-08-24 journal entry describes: `git fetch` + `git rebase origin/main`, which silently drops the commit whose content already landed and keeps only what's new. Knowing the correct pattern once is not the same as applying it by default the next time the same condition recurs — the close-session branch for this very entry was cut fresh from `origin/main` *before* writing anything, specifically because of this.

#### A live PR became the verification instrument for the bug it was fixing

PR #74 fixed `delete_branch_on_merge`, and its own remote branch surviving the merge — because the fix hadn't landed yet at push time — was direct, first-party evidence the bug was real rather than theoretical. The very next PR's branch auto-deleting cleanly was equally direct evidence the fix worked. Neither required a separate test; the repository's own PR lifecycle was the experiment.
