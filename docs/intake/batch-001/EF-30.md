## Claim

Arcane records defect severity as prose but has no mechanism that changes priority, release eligibility, escalation, ownership, or risk acceptance. A fully diagnosed field-confirmed data-loss bug with a specified regression test remained open for 17 days while routine backlog work continued.

## Verification

Confirmed. Commit `5bc1b72` added the update defect to `TODO.md` on 2026-07-14 as **"BUG (confirmed — DATA LOSS)"** with the complete root cause, affected files, missing backup, ownership fix, and regression test. EF-25 independently rediscovered the same facts on 2026-07-31. No fix landed between the two reports, and the original `.bak` docstring defect remained open alongside it.

The historical TODO audit shows this is a pattern rather than one missed item. Using a strict definition — an open item with direct source diagnosis, an accepted-but-unimplemented defect decision, or an explicit field/dogfood observation — nine confirmed or observed defects were open by this intake, including EF-25; eight others were already present:

2. `spell-commit-work` performed an unexpected self-merge — field test, first filed 2026-07-10; now EF-28, High.
3. `update.ts` promises `.bak` files that do not exist — source diagnosis, first filed 2026-07-11; same root as EF-25.
4. ARC-012 parity guard was accepted but never implemented — backlog filing 2026-07-11; underlying accepted decision dated 2026-06-20.
5. Org-token lint is wired with an empty pattern list — source diagnosis, first filed 2026-07-11; now EF-26, High.

The oldest TODO defect filing was 21 days old on 2026-07-31. ARC-012's underlying accepted decision was 41 days old. None of the pre-batch TODO entries had a machine-readable or consistently formatted severity field, including the item whose title literally said DATA LOSS. At least three of the eight other defects are now independently classified High (EF-26, EF-27, EF-28). Routine documentation and backlog commits continued after 2026-07-14 while EF-25 remained unactioned.

## Impact

Detection works, but detection has no consequence. Critical wording competes as an undifferentiated checkbox beside routine features and copy edits. A maintainer or agent can truthfully record "DATA LOSS," continue lower-risk work, and still satisfy the backlog process. Repeated rediscovery consumes investigation time without reducing user exposure.

This is EF-24 one level up. EF-24 requires normative rules to name an enforcement mode; EF-30 requires recorded severity to cause an observable workflow transition. Keep them separate: EF-24 classifies controls generally, while EF-30 defines the incident-priority and release-risk mechanism.

## Proposed fix

Decide which enforceable mechanism makes a confirmed data-loss item impossible to leave as an ordinary open checkbox. The ADR must select one or a layered combination:

1. **Release gate:** block release while an unaccepted Critical/High data-integrity defect is open.
2. **Severity-ordered backlog:** move confirmed incidents into a structured queue ordered before routine work, with owner and response deadline.
3. **Doctor/build check:** detect unresolved severity-tagged incidents and fail or warn according to policy.
4. **Explicit risk acceptance:** permit deferral only through a dated maintainer sign-off recording scope, exposure, mitigation, review date, and release effect.

The mechanism must be machine-readable, visible, and fail closed for missing severity on confirmed data-integrity/security defects. It must distinguish research uncertainty from a source-confirmed defect and must not allow emphatic prose such as "DATA LOSS" to substitute for structured severity.

Acceptance requires retroactively classifying the current open defect inventory, assigning ownership and disposition, and demonstrating that EF-25 would have escalated on 2026-07-14 under the chosen mechanism. A future-only policy would repeat EF-24's failure mode.

## Open questions

Which severities block release, and does the gate apply only to data integrity/security or all High defects? What response deadline is appropriate for a solo maintainer? Where does risk acceptance live so it is reviewable without exposing private deployment details? How are false positives or severity downgrades approved?
