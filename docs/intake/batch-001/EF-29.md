## Claim

Git governance requires a session branch as the first action before edits, but `spell-open-session` treats `main` as healthy and only validates or renames an already noncompliant branch.

## Verification

Confirmed. [git-conventions.md](../../../src/assets/.arcane/governance/git-conventions.md#L198-L220) requires creating `sessions/YYYY-MM-DD-topic-slug` as the first action of every interactive session. [spell-open-session.prompt.md](../../../src/assets/.github/prompts/spell-open-session.prompt.md#L50-L63) checks the current branch, considers `main` the expected baseline, and defines renaming only for a noncompliant current branch. It never creates the required session branch when opening on `main`, even though the same prompt later generates a deterministic session name.

## Impact

The normal open-session path leaves work on `main` until another spell notices, so the first edits can violate the branch policy the opener was supposed to establish.

A naive fix would create the opposite defect in repositories with no remote. There, a session branch has no PR or other merge path; `spell-close-session` cannot complete it, dead branches accumulate, and trunk never advances. The tier-A deployment adopted trunk-only operation for exactly this reason. Branch ceremony without an enforcement or integration effect is not protection.

## Proposed fix

Design EF-29 and EF-19 together as one remote-capability decision expressed in opposite lifecycle spells:

- **Usable remote and merge path:** create or switch to the compliant `sessions/YYYY-MM-DD-topic-slug` branch lazily, immediately before the first repository mutation.
- **No remote:** remain on the repository's trunk and use EF-19's local-only close path. Do not create a session branch that nothing can merge.

Prefer lazy creation at first mutation over a declared read-only exemption. Whether a session will remain read-only is not knowable at open time; a session can begin as advice and become substantial repository work. Lazy creation is based on the observable action about to occur and therefore corrects itself as the session changes. A declaration made at open time does not.

The mutation guard must account for worktree-backed sessions without switching another workspace's branch. Add scenarios for remote + read-only (no branch), remote + first mutation (create branch before edit), no remote + mutation (stay on trunk), compliant existing session branch, noncompliant unpushed branch, active-PR branch, and worktree branch. Verify the corresponding close-session path can integrate every branch state the opener creates.

## Open questions

What constitutes a usable remote and merge path: any configured remote, a writable upstream, or a supported PR provider? If a remote is added or removed mid-session, which observed state governs the next mutation and close path?
