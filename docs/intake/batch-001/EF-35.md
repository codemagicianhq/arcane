## Claim

Arcane's governance corpus states secret-handling rules repeatedly and in detail — use secret
references rather than literals, keep credentials out of version control, keep them off the command
line, give agents scoped credentials — but nothing in this repository, and nothing Arcane installs
into a consuming repository, ever *checks* whether a secret was actually committed. The policy is
enforced by intention only. No scanner runs on the commit path, on the push path, in CI, or on
demand as a mechanical step; the sole "detection" is an instruction asking an AI agent to look.

## Verification

Checked against HEAD (`0.20.0`) on 2026-08-23.

A repository-wide search for every common scanner — `gitleaks`, `trufflehog`, `detect-secrets`,
`git-secrets`, `secretlint`, `ggshield` — returns exactly one hit, and it is prose rather than
configuration: `features/push-safety/PRD.md:80`, which is the note that prompted this finding. There
is no scanner dependency in `package.json`, no scanner config file, and no scanner invocation in any
of the three workflows (`.github/workflows/ci.yml`, `publish.yml`, `release-drift.yml`). A search of
`.github/` for `secret scanning` or `push protection` returns nothing, so GitHub's own platform-side
scanning is not configured through anything version-controlled here either — if it is enabled at all,
it is enabled in repository settings that this repository cannot see, assert, or reproduce for a
consuming repo.

The commit path is likewise clear of any check: `.husky/pre-commit` runs `npm run lint && npm run
typecheck` and nothing else.

The policy side is genuinely substantial, which is what makes the gap notable rather than merely
absent. `src/assets/.arcane/governance/authentication-strategy.md:18,26,30` mandates the
secret-reference pattern and storage outside version control.
`src/assets/.arcane/governance/agent-policies.md:407,411` requires tokens sourced from secret
references and forbids secrets on the command line.
`src/assets/.arcane/governance/hardening-checklist.md:96,104` repeats it as a checklist item.
`src/assets/.arcane/governance/git-conventions.md:747` lists `.env`, `*.pem`, `*.key` among the paths
a repository should ignore. `src/assets/.arcane/governance/threat-model.md:52` goes further and
records token/credential exposure as **Mitigated**.

The closest thing to detection is `src/assets/.github/prompts/spell-security-review.prompt.md:66-69`,
a "Secrets detection" step instructing the agent to "Scan for API keys, tokens, passwords, connection
strings in code." That is an agent reading files it chose to read, only when a human invokes the
spell, with no deterministic coverage guarantee and no failure mode that blocks anything. It is a
review aid, not a control. Treating it as detection is the specific confusion this finding exists to
prevent — and `threat-model.md:52`'s "Mitigated" already reflects that confusion, since the listed
mitigation is entirely a set of storage conventions with no verification step behind them.

## Impact

A committed secret is not a defect that can be fixed by fixing the file. It is in history, in every
clone already taken, and in the remote's backups; remediation means rotating the credential, not
editing the repository. That asymmetry is why detection belongs *before* the write, and why a policy
without detection is weaker than its own documentation suggests.

The specific hazard here is compounded by what Arcane is for. Arcane drives autonomous agents that
write files, run commands, and commit. An agent that pastes a connection string into a config file
while wiring up a service has violated a policy it may well have read, and there is no step anywhere
between that keystroke and a public remote that would notice. `ARC-034`'s push-safety work
(shipped 0.20.0) now blocks pushes in repositories the operator marks sensitive, which narrows the
blast radius for those repositories specifically — but it is a blanket block chosen per repository,
not a check that inspects content, and it does nothing for the ordinary `open` repository where most
commits happen.

The governance overclaim is its own harm, separate from the missing tool. `threat-model.md:52` tells
a reader that credential exposure is mitigated. A reader who believes that is *less* likely to add
scanning, which is the mechanism by which a control believed stronger than it is produces the
carelessness it was meant to prevent — the same failure shape ARC-034 §1 argues against in the push
case.

## Proposed fix

Route to an ADR rather than straight to implementation, because the substantive decision is not
"which scanner" but **where the check binds and what it is allowed to block**, and that decision
interacts with three things already shipped.

The ADR should settle:

1. **Bind point.** A pre-commit check catches the secret before it enters history at all, which is
   the only point where remediation is free — but it is the hook slot already occupied by
   `lint && typecheck`, and it is the slot users bypass with `--no-verify` most casually. A pre-push
   check catches less (the secret is already in local history) but sits on the boundary that
   matters. CI catches everything reliably and blocks nothing in time. These are not exclusive;
   the ADR should say which are required versus recommended.
2. **Interaction with ARC-034's hook.** Push safety already installs a `pre-push` hook and already
   owns `core.hooksPath`, with an explicit collision guard that refuses to clobber a foreign hooks
   path. A scanner arriving later must extend that mechanism rather than compete for the same slot.
   This is the main reason to decide by ADR before writing code.
3. **Self-host versus consuming repos.** Arcane's own repository and the assets it installs are
   separate questions with a parity constraint between them
   (`npm run check:self-host-parity`). A scanner added only to this repository would be a governance
   tool that does not ship, which is the inversion Arcane exists to avoid.
4. **False-positive posture.** A scanner that blocks on test fixtures and example keys gets disabled
   within a week, at which point the repository is worse off than before because the disabling is
   invisible. Whatever is chosen needs a documented allowlist mechanism and a decision about whether
   a bypass is recorded in the manifest the way `push_policy_unblocked_at` is.

Independent of the tooling decision, `threat-model.md:52` should stop reading **Mitigated** for
token/credential exposure and instead state the actual position: storage conventions are documented,
detection is not implemented. That correction is small, is not blocked on the ADR, and removes the
overclaim immediately.

## Open questions

- Does the operator want detection to be mandatory for every Arcane-managed repository, or opt-in on
  the same axis as `content_sensitivity`/`push_policy`? A per-repository field would fit the existing
  manifest contract (ARC-032's persist-once pattern) but adds a fourth security-posture field.
- Should a scanner ship as a registry component (visible, updatable, deletable by the operator) or be
  embedded the way ARC-034's pre-push hook ended up being, precisely so it cannot be deleted out from
  under its own configuration? ARC-034 §3 records that deviation and its reasoning; the same argument
  may or may not apply here.
- Is GitHub's native secret scanning with push protection sufficient for repositories hosted there,
  reducing this to a documentation task plus a `doctor` check that reports whether it is on? That
  depends on whether Arcane is willing to depend on a platform setting it cannot read from a
  version-controlled file.
