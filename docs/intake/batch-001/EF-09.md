## Claim

Arcane initializes the same workflow for repositories containing broadly sensitive documents and provides no durable safeguard against pushing permanent Git history to a remote.

## Verification

Confirmed as an absent capability, not as a defect in an existing hook. The component registry contains no hook, push guard, or sensitive-repository component in [registry.ts](../../../src/modules/registry.ts#L13-L182). The shipped Git standard assumes pushes and remote PRs, for example [git-conventions.md](../../../src/assets/.arcane/governance/git-conventions.md#L244-L257). The threat model recognizes local sensitive data at [threat-model.md](../../../src/assets/.arcane/governance/threat-model.md#L16-L29) but does not define a no-push repository mode. Repository-wide source search found no `pre-push` or `core.hooksPath` guidance.

## Impact

One mistaken push can distribute sensitive history permanently. A local `.git/hooks/pre-push` workaround is not versioned and therefore cannot be treated as a durable framework control.

## Proposed fix

Research whether Git should cover the archive at all before specifying controls. Compare versioned hooks, disabled push URLs, data scanners, encryption, remote policy, and a split model where only working documents enter Git. The PRD must state the threat model and bypass/recovery behavior.

## Open questions

Is the repository local-only, remotely backed up, or collaboration-enabled? What data classes are in scope, and is preventing all pushes an intended invariant or an operator override?
