## Claim

The asset build declares org-token portability lint as a failing gate, but its only pattern list is empty, so the mechanism cannot detect any organization-specific token.

## Verification

Confirmed. [copy-assets.ts](../../../scripts/copy-assets.ts#L69-L78) describes the lint as the D2 distributability gate, sets `ORG_TOKEN_MODE` to `fail`, and initializes `ORG_TOKEN_PATTERNS` to an empty array. The scan loops only over that array at [copy-assets.ts](../../../scripts/copy-assets.ts#L80-L104), so it deterministically returns no org-token findings for every prompt. The build later treats findings as fatal, but that branch is unreachable while the rule set is empty.

## Impact

The release process presents an inert control as an OSS leakage gate. Organization names, internal hosts, venture names, and other configured classes can ship while CI remains green.

Because the gate has never had a functional rule set, current source provides no assurance about artifacts already published. This is not only a forward-looking exposure: if an internal identifier exists in v0.14.0 or an earlier package, every consuming repository that installed that release may have copied it into its working tree and permanent Git history. The first remediation question is therefore whether leakage already happened, not only how to prevent the next occurrence.

## Proposed fix

Before changing the gate, run a retrospective exposure scan over the current distributable and every retrievable published release, including v0.14.0 and prior npm tarballs. Scan the exact packaged assets rather than only the current source tree. Record affected package versions and file paths without copying sensitive values into public reports. If leakage is found, define consumer remediation that accounts for files already copied by `spell init` and committed to downstream Git history; a source-only removal is insufficient.

Then either populate a maintained, tested rule source or remove the claim that the build enforces this class of leak. Prefer a configuration-driven denylist with safe defaults and fixtures proving both detection and placeholder exclusions.

Verification requires a negative regression test: seed a known-bad organization token into a distributable prompt fixture, run the real build/gate, and assert that it fails with the offending file identified. A test that executes the empty scanner and observes a green build proves nothing, because that is the current broken behavior. Add a complementary positive fixture showing that documented `{UPPER_SNAKE}` placeholders remain allowed.

## Recurrence evidence

On 2026-08-02, the self-host parity design became the fourth observed recurrence of this lesson. A test against the already-clean root tree would have proved only that no drift was present at that moment. The accepted parity gate instead mutates a generated root fixture, runs the exact npm command wired into CI, and asserts a nonzero exit with the drifted path identified.

## Open questions

Which tokens can be public defaults without embedding Code Magician-specific identifiers in the package, and which must be supplied by repository configuration? Which historical npm versions remain retrievable, and what notification or history-rewrite guidance is proportionate if a prior release copied an internal identifier into consuming repositories?
