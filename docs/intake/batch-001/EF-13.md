## Claim

Read-only Git commands can leave locks on a filesystem that rejects unlink operations, and Arcane neither suppresses optional locks nor warns when a repository is inside a synchronized or restricted filesystem.

## Verification

Partially source-verified but not reproduced in this checkout. Arcane's executable Git helper runs plain `git status --porcelain -uall` with no optional-lock policy at [git.ts](../../../src/modules/git.ts#L1-L13). Canonical prompts and governance contain no `--no-optional-locks` or `GIT_OPTIONAL_LOCKS=0`, and init only uses the helper as a dirty-tree probe at [init.ts](../../../src/commands/init.ts#L138-L157). No sync-root detection appears in the init path.

The reported unlink failure, stale lock, and next-command failure require the external deletion-restricted filesystem and could not be reproduced safely here. The sync-client cause is explicitly only a precaution; current source does not establish it as the cause. The submitted mitigation also needs command-level testing rather than blanket application to every `log` or `diff`.

## Impact

If reproduced, read-only state inspection can damage availability for the next Git operation and attribute the failure to the wrong agent. Sync-root concurrency adds a separate integrity risk.

## Proposed fix

Build a restricted-filesystem test harness first. Test `git --no-optional-locks <command>` and `GIT_OPTIONAL_LOCKS=0` per command class, then define a framework-wide read-only Git contract. Research sync-root detection separately and warn rather than assign causality without evidence.

## Open questions

Which bridge/filesystem produced the failure, which Git for Windows version was used, and can the submitting deployment provide a reproducible mount with unlink denied?
