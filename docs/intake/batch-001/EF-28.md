## Claim

Arcane governance requires human approval before commits in interactive sessions and permits autonomous self-merge only at Magus+, while core commit spells execute commits and PR completion without checking either condition.

## Verification

Confirmed. [git-conventions.md](../../../src/assets/.arcane/governance/git-conventions.md#L328-L339) requires every interactive tool to present the commit and wait for human approval, and limits autonomous self-commit/self-merge by power level. [spell-commit-work.prompt.md](../../../src/assets/.github/prompts/spell-commit-work.prompt.md#L111-L116) instead says to execute the commit immediately, then runs a PR completion lifecycle without resolving interaction mode or power level. [spell-close-session.prompt.md](../../../src/assets/.github/prompts/spell-close-session.prompt.md#L103-L120) likewise stages and commits immediately with "no approval wait" and delegates to that completion flow.

The power-level and execution-permission inputs a corrected spell would consult are themselves unchecked YAML fields, as verified in EF-27. EF-28 remains the spell-layer enforcement bug; EF-27 independently owns validation and compatibility at the loader boundary. Both must be fixed for the autonomy gate to be trustworthy.

## Impact

An interactive agent can create commits without the mandated approval, and a below-Magus agent can reach completion behavior reserved for higher autonomy. The policy fails silently because successful Git and provider commands look like authorized execution.

The tier-A deployment exercised this path six times in one session. Six commits were executed through `spell-commit-work` without an autonomy or structured approval check. A human approved each commit only because the restricted-filesystem failures in EF-13 and EF-20 prevented the agent from running Git and forced every command back to the operator's shell. The autonomy gate was therefore enforced by an unrelated bug, not by Arcane.

That accidental dependency is dangerous: fix EF-13 and EF-20 in isolation, restore reliable agent-run Git, and the same six commits can execute automatically with no replacement authorization gate. Two availability defects are currently load-bearing for a third control by accident.

## Proposed fix

Make interaction context and effective power level explicit inputs to commit-capable spells. Require a structured approval gate for interactive commits and halt PR completion below Magus. Scope the fix to both authorization points:

1. **Commit:** no interactive `git commit` executes without an authenticated operator approval tied to the exact staged diff and proposed message.
2. **Merge:** `spell-close-session` step 9c and every delegated PR flow must gate `pr update --status completed`, auto-complete, or equivalent self-merge behavior on validated Magus+ authority. Approval to commit is not approval to merge.

Degradation must be visible. When interaction context, consent provenance, or effective power level is missing or invalid, the spell must choose the least-authorized path, print that it has downgraded, identify the missing/invalid input, and state the action now requiring human approval. A silent fallback to asking the human is safer than proceeding but still fails operationally because the operator cannot distinguish a control gate from a routine prompt.

Add prompt-level tests or fixtures that verify interactive, autonomous-below-Magus, autonomous-Magus+, invalid/missing authority, commit-approved-but-merge-not-approved, and visible-degradation paths.

Consume only loader-validated autonomy data from EF-27. Missing, invalid, or unavailable effective power level must fail closed to the least-authorized path; it must never default upward or infer permission from successful Git/provider access.

## Open questions

Where is effective per-repository delegation persisted, and which actor is authoritative when the roster default differs from an operator-granted session delegation? How is operator approval bound to one exact commit or merge action so it cannot be replayed for a later operation?
