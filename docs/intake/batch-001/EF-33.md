## Claim

An agent or operator inspecting a Git repository through a cross-filesystem bridge (e.g. a Linux-side mount of a Windows host, a remote/SSH-mounted view, a container bind-mount with a different root) can have `git worktree list` correctly and honestly report live, healthy linked worktrees as `prunable`, because the worktree's registered absolute path does not resolve to an existing directory from that vantage point — even though the directory exists and is valid from the machine that actually owns it.

## Verification

Confirmed as a live near-miss during this session. The operator read `git worktree list` from a Linux-side view of this repository and observed the primary worktree only, with the remaining eight linked worktrees registered at Windows `X:\Code\CodeMagician\arcane\...` paths. Those paths do not exist as such from the Linux mount, so Git correctly marked all eight as `prunable` for that read — a truthful report of what that vantage point could see, not a bug in Git.

Independently, from the Windows side (the worktrees' actual owning environment), `git worktree list --porcelain` showed no `prunable` annotations, `Test-Path` confirmed all nine directories present on disk, and `git worktree prune -v` removed zero entries. The two observations are both accurate for their respective vantage points; only one of them describes the worktrees a destructive operation would actually affect.

The operator had already instructed running `git worktree prune` before this was caught. On Windows, that command is a harmless no-op, because nothing there is prunable. Had the same `git worktree prune` been issued from the bridge-mounted Linux view instead, Git would have deregistered all eight cross-platform-registered worktrees — none of which were actually dead — using the exact same command, on the exact same repository, with no error and no warning distinguishing "this path is gone" from "this path is not visible from where I am standing."

## Impact

A read that is individually correct for its vantage point can still be globally false about the resource it describes, and nothing in `git worktree list`'s output distinguishes "confirmed absent" from "not resolvable from this process's filesystem view." An agent or operator who trusts that report and acts on it (`git worktree prune`, or worse, manual deletion of what looks like now-orphaned `.git/worktrees/<name>` metadata) can destroy live work with a command that appears fully justified by the tool's own output. This is a distinct failure shape from EF-13/EF-20 (agent-run Git write operations failing or hanging under restricted/remote filesystem access): those are about writes not completing; this is about reads reporting false state with high confidence, and a destructive command trusting that state.

## Proposed fix

Before running any Git command with irreversible effects on worktree, branch, or ref state (`worktree prune`, `worktree remove`, `gc --prune=now`, branch deletion) in an environment where the repository or its linked worktrees may be reached through more than one filesystem view (bridged mounts, remote-mounted volumes, container bind-mounts, path translation layers), require an explicit same-vantage-point confirmation step: resolve and display the registered worktree path exactly as Git sees it, and require the operator or agent to confirm that path is meaningful from the CURRENT process's filesystem, not just that the repository responds. Cross-referencing `git worktree list --porcelain` output against an independent path-existence check (e.g. `Test-Path` / `os.path.exists` in the actual runtime, not assumed from the same command's own report) before treating any entry as prunable would have caught this before the instruction to prune was ever given.

## Required tests

Not independently testable in CI (the defect is about cross-machine/cross-mount filesystem visibility, which a single CI runner cannot reproduce). Document this as a standing operational caution in the relevant Git-operations governance doc instead, and require the confirmation step above to be followed manually whenever an agent operates across a filesystem bridge.
