## Claim

`arcane update` force-overwrites session-continuity files that the registry explicitly marks as user-owned and install-once. The promised `.bak` recovery files are never created, and the update suite has no regression test protecting continuity content.

## Verification

Confirmed. `RegistryComponent.skipExisting` is documented for user-owned files that must be created on first init but never overwritten on re-init or update at [types.ts](../../../src/types.ts#L20-L35). The `session-continuity` component sets that flag for `TODO.md`, `DECISIONS.md`, `ai-context/system-prompt-context.md`, and `journal/.gitkeep` at [registry.ts](../../../src/modules/registry.ts#L168-L181). Init honors it by skipping an existing destination at [init.ts](../../../src/commands/init.ts#L228-L243).

Update does not inspect `skipExisting`. It iterates every registered file and calls `copyFile(..., { force: true })` at [update.ts](../../../src/commands/update.ts#L73-L95), replacing accumulated continuity content with package templates. The same command promises `.bak` siblings for every overwritten file at [update.ts](../../../src/commands/update.ts#L12-L18), but neither the update path nor the copier creates a backup. The dry-run test explicitly expects no `.bak` for a managed file at [update.test.ts](../../../test/update.test.ts#L241-L267), and no update test covers `session-continuity`, `skipExisting`, `TODO.md`, `DECISIONS.md`, or `system-prompt-context.md`.

## Impact

This is destructive data loss, not cosmetic drift. A live consuming repository can lose its full backlog, decision history, and next-session context in one successful update command. The affected operation reports success and provides no recovery artifact.

## Proposed fix

Treat EF-25 as the first implementation priority and ship an emergency mitigation ahead of the full ownership fix:

1. Refuse `arcane update` when the working tree is dirty. Print the changed-file count and require the operator to commit or otherwise make the tree clean before retrying; never stash or discard changes automatically.
2. Refuse update when the repository has no commits or is not a Git repository. Without a committed baseline there is no recovery source if update replaces user content.
3. Add a prominent console warning and current-version release note: **commit your work before updating Arcane**. State that update in the affected version can overwrite managed continuity files and that a clean committed baseline is required for recovery.

This mitigation is deliberately incomplete. A clean working tree does not make overwriting user-owned files correct; it only prevents unrecoverable loss and makes an accidental replacement recoverable from Git while the permanent fix is developed.

Make update honor the ownership semantics declared by the registry. Files in a `skipExisting` or more explicitly named `preserveOnUpdate`/`scaffoldOnly` component must remain untouched when present; missing files may be backfilled. Resolve the `.bak` contract in the same change: either implement backups for managed files that are legitimately overwritten or remove the false promise, but preserved continuity files must not rely on backups as their primary safety mechanism.

Evaluate whether `.bak` is the right contract at all, as part of this fix rather than a follow-up. For continuity files, it is not: the registry declares them user-owned, so update must not write them and a backup cannot legitimize that write. Backup semantics apply only to files the ownership model explicitly permits update to replace; if no such recovery guarantee is intended, remove the promise and document the actual behavior.

The fix is incomplete without a regression test. Add an end-to-end update test that initializes a repository, writes distinct operator content into `TODO.md`, `DECISIONS.md`, and `ai-context/system-prompt-context.md`, updates from an older manifest version, and asserts every edit survives byte-for-byte while the manifest/version and ordinary managed files update normally. Also assert missing continuity files are backfilled if that remains the intended contract.

## Open questions

Should the existing `skipExisting` flag define both re-init and update behavior, or should the registry expose separate `scaffoldOnly` and `preserveOnUpdate` semantics? Which non-continuity managed files are intentionally replaceable, merge-managed, or user-owned?
