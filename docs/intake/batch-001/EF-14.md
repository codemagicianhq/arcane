## Claim

Arcane already persists one repo-level behavioral decision (`profile`) but does not persist the parallel repo-level tracking decision (`tracking_mode` / `external_provider`). Because `.arcane.json` has nowhere to store tracker config, spells ask repeatedly per session.

## Verification

Confirmed as one merged finding, with explicit operator confirmation recorded.

The persistence precedent already exists in core code:

- `profile` is selected once during init at [init.ts](../../../src/commands/init.ts#L160-L176).
- `ArcaneManifest` stores exactly four fields (`version`, `profile`, `installedAt`, `components`) at [types.ts](../../../src/types.ts#L12-L17).
- `runInit` writes exactly that shape at [init.ts](../../../src/commands/init.ts#L272-L279).
- Operational commands treat `.arcane.json` as canonical persistent state (for example, `status`) at [status.ts](../../../src/commands/status.ts#L1-L30).

Tracker settings follow a different path. These settings describe where work items live; they do not describe repository visibility, Git remotes, or the pull-request review surface. In this repository, work items live in `TODO.md` and `docs/intake/`, while GitHub is only the review surface.

- `spell-open-session` requires `tracking_mode` / `external_provider`, resolves from `.arcane.json` or PRD frontmatter, and asks the operator if missing at [spell-open-session.prompt.md](../../../src/assets/.github/prompts/spell-open-session.prompt.md#L64-L69).
- `spell-plan` applies the same fallback rule (read config, ask if unset) at [spell-plan.prompt.md](../../../src/assets/.github/prompts/spell-plan.prompt.md#L30-L37).
- No runtime enum or schema currently types these values: `tracking_mode` and `external_provider` are absent from [types.ts](../../../src/types.ts) and `src/config/`. The defect is therefore both missing persistence and missing type-level validation.

User-side confirmation (2026-08-01): operator selected `tracking_mode=internal` during session-open because no persisted value was available. This repository currently has no `.arcane.json` file at root; `doctor` would report that as not initialized at [doctor.ts](../../../src/commands/doctor.ts#L83-L105). This repo dogfoods `.arcane/` and `.claude/` but ships no manifest, so any spell expecting tracker config from `.arcane.json` must prompt every run.

Self-hosting decision (2026-08-02): Arcane uses a committed source manifest at [src/assets/.arcane.json](../../../src/assets/.arcane.json), marked `selfHosted: true`, with `tracking_mode: internal` and no external provider. The generated root `.arcane.json` remains gitignored because it is installed-target state, not source truth. Config-resolving spells must resolve the generated root manifest first, then the committed self-hosted source manifest, then PRD frontmatter, and ask only when all three are absent. `doctor` recognizes the committed marker as a narrow self-hosting exemption; it does not exempt an unmarked or externally tracked source manifest.

Wording note: the session-scoped phrasing in open-session output ("for this session") is a symptom of missing persistence, not a separate defect. Once tracker config persists like `profile`, the wording naturally becomes stable and honest without extra prompt logic.

Label-ambiguity note: `internal` / `external` is ambiguous about what is being tracked. In live use, the labels were read as repository visibility/remote-push intent (private docs repo versus pushing to a remote) rather than work-item location. The session still landed on the correct value by luck. A wrong guess is operationally significant: selecting `external` triggers spells to attempt external work-item creation/linkage where no tracker exists.

## Impact

Persistent tracker choices remain in operator memory. Spells repeatedly ask, silently infer defaults, or run with partial context. This duplicates intent capture with docs-mode profiling in [EF-04](EF-04.md): repo type and tracker mode are currently asked as separate decisions even though they largely answer the same classification question.

## Proposed fix

Model the remediation on the existing `profile` lifecycle instead of adding another per-session fallback:

1. Persist work-item destination as first-class repo state in `.arcane.json` with the same contract as `profile`: chosen once at init (or explicit reconfigure), then reused by all spells. Keep the GitHub/Azure DevOps/GitLab review surface separate from this setting.
2. Add versioned schema fields and TypeScript unions for `tracking_mode` and `external_provider` in the canonical manifest schema, then backfill on update without overwriting existing operator values. Reject unsupported values rather than silently treating them as a provider.
3. Replace ambiguous labels with meaning-first wording at selection time:
   - `Track work in this repo (TODO.md / PRDs)`
   - `Track work in an external tracker (Azure DevOps / Jira / other)`
     If this value is asked once at init, label clarity becomes more important, not less, because the operator is setting durable behavior.
4. Derive defaults from profile to avoid double questioning:
   - docs/journal profile path defaults to `tracking_mode=internal` and no external provider.
   - artifact-producing profiles still choose internal vs external once, then persist.
5. Keep broader schema unification (operator identity, business roots, provider coordinates, repo lists) under the same migration so one shape is evolved once, not patched ad hoc.

Cross-reference [EF-04](EF-04.md): profile selection and tracker mode are coupled classification decisions and should be asked as one coherent setup flow, not separate recurring prompts.

## Open questions

The remaining schema question is which additional repository-level fields belong in the manifest and how secrets are prohibited from both storage and prompt placeholders. The self-hosting location and doctor behavior are no longer open: source truth is `src/assets/.arcane.json`; installed target state is root `.arcane.json`.
