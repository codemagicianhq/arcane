## Claim

The original framing, "spells treat dispatch as completion," is contradicted by current source. The surviving claim is narrower: `spell-close-session` states a verifiability rule in prose but has no structured pending-verification state or in-flight check before writing the handoff. "Only mark items done if verifiable from context" does not distinguish "I can see I started it" from "I can see it finished." An in-flight CI run is verifiable in the first sense and not the second, which leaves the reported failure mode to agent judgment.

## Verification

Confirmed after re-scoping. The original framing is explicitly contradicted by the rule "Do not invent completions - only mark items done if verifiable from context" at [spell-close-session.prompt.md](../../../src/assets/.github/prompts/spell-close-session.prompt.md#L181-L184). The handoff distinguishes `Last completed step` from `Next concrete action` at [spell-close-session.prompt.md](../../../src/assets/.github/prompts/spell-close-session.prompt.md#L65-L78), so current source does not instruct agents to report dispatch as success.

The narrower defect does reproduce. The handoff schema has no `Pending Verification` field, and the workflow proceeds from commit and PR actions to returning to `main` without checking CI, deployment, or other asynchronous work at [spell-close-session.prompt.md](../../../src/assets/.github/prompts/spell-close-session.prompt.md#L103-L127). Source search found no in-flight-work check or operational definition distinguishing observed dispatch from observed completion. The prose rule therefore depends entirely on agent interpretation and can fail silently under load.

## Impact

A handoff can encode an unverified outcome as fact even though the spell contains a general warning against doing so. The next session trusts that handoff as source context, so one ambiguous completion judgment can propagate a false premise into later work.

## Decision rationale

> Decision-support explanation provided during intake by the Opus 5 High model. It clarified why the maintainer chose to keep and re-scope this item.

The whole thing is one distinction: **"I started it" is not "it worked."**

Here's the plain version.

You hand a letter to the post office, then write in your diary: _"Delivered the letter."_ You didn't deliver anything - you handed it over. Maybe it arrives, maybe it's lost. But next week someone reads your diary and treats it as fact.

That's what happened. `spell-close-session` finished a session while two builds were still running, and wrote the session notes as though they'd succeeded. One had **already failed** at the moment of writing. The other failed shortly after. So the journal, the TODO, and the handoff all recorded things that never happened, and a correction PR was needed the same day.

The reason this is a framework problem and not a one-off is that it repeats at every layer, each one further from the truth:

| What the system reports           | What's actually true                                             |
| --------------------------------- | ---------------------------------------------------------------- |
| The build was **triggered**       | It might still fail                                              |
| The build **passed**              | The code might not have reached the server                       |
| The code was **published**        | Users might still be running the old version                     |
| Git said the **commit succeeded** | The lock file it was supposed to clean up is still sitting there |

That last row is ours. It's the stale `.git/index.lock` that kept blocking the consuming deployment. Git reported success; the cleanup hadn't happened; the failure showed up on the _next_ command. It has the same shape as EF-13, which is why the findings must be reconciled: it is the same class of defect in a place nobody was looking.

**Why it matters more than a typo in a log:** the handoff is the first thing the next session reads, and it's trusted completely. A note saying "deployed successfully" doesn't just fail to inform - it installs a false belief, and the next agent builds on top of it. Wrong is worse than missing.

**What the verification disagreement was actually about:** Arcane already has a rule: _"Do not invent completions - only mark items done if verifiable from context."_ Good rule. Its problem is the phrase **"verifiable from context."** If you can see a build was started, is that "verifiable"? In one sense yes - you can see it exists. In the sense that matters, no - you can't see whether it finished. The rule doesn't distinguish those, so an agent in a hurry can read it as permission.

And there's no machinery behind it. Nothing in Arcane can ask _"is something I kicked off still running?"_, and there's no structured way for a session to write down **"I couldn't check this."** That last one is the real gap: _"I don't know yet"_ is a valid and useful state to record. Without it, the workflow pressures the agent toward claiming completion or saying nothing.

## Proposed fix

Add a structured `Pending Verification` block to the handoff and require an in-flight check before it is written. Async work must be recorded as dispatched, pending, succeeded, failed, or unverifiable; only succeeded work may be described as complete. When the spell cannot query the target system, it must leave the item pending and state the exact verification action.

## Open questions

Which asynchronous systems can `spell-close-session` detect generically, and which require provider-specific adapters? What bounded wait policy should apply before the spell records work as pending rather than blocking session closure?
