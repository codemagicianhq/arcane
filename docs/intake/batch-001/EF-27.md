## Claim

Agent rosters declare a schema version, and agent definitions carry power-level and execution permissions, but both loaders accept parsed YAML through unchecked TypeScript casts. They never reject or migrate incompatible roster versions and never validate the autonomy values that downstream gates would need to trust.

## Verification

Confirmed. `AgentRoster` requires `schema_version` at [types.ts](../../../src/types.ts#L145-L155), and roster creation writes version `2` at [agents.ts](../../../src/modules/agents.ts#L156-L166). `loadRoster` returns `parse(content) as AgentRoster` without checking that field or any required structure at [agent-loader.ts](../../../src/modules/agent-loader.ts#L78-L94).

Agent definitions are loaded through the same unchecked-cast pattern at [agent-loader.ts](../../../src/modules/agent-loader.ts#L39-L53) and [agent-loader.ts](../../../src/modules/agent-loader.ts#L58-L74). Those definitions include `default_power_level` and `exec_allowed` at [types.ts](../../../src/types.ts#L94-L99). The generator reads both unchecked values into generated autonomy instructions at [agent-generator.ts](../../../src/modules/agent-generator.ts#L60-L70). For example, the orchestrator definition declares `Magus` and execution permission at [orchestrator.yaml](../../../src/assets/agents/orchestrator.yaml#L42-L47).

EF-27 and EF-28 are the same failure class at opposite boundaries but remain separate bugs. EF-27 makes the prospective gate input untrustworthy at the loader; EF-28 fails to consult or enforce that input in commit-capable spells. A gate built for EF-28 without EF-27 would read values that were never validated.

## Impact

Malformed or future-version YAML can load successfully and fail later as missing fields, incorrect generation, partial synchronization, or incorrect autonomy instructions. A missing, misspelled, or future power level can reach downstream generation instead of stopping at the trust boundary. The version and permission fields communicate compatibility and authorization safety that does not exist.

## Proposed fix

Validate parsed roster and definition structures at the loader boundary before list, sync, generation, or any future authorization decision. Fail closed: an unsupported, missing, malformed, or future schema version must refuse to load with an actionable compatibility error, never degrade to a partial parse. Validate `default_power_level`, `exec_allowed`, tool permissions, spawn permissions, and every other security- or autonomy-relevant field against closed enums and required shapes.

Define explicit migrations only for versions the current CLI deliberately supports. Add fixtures for malformed YAML, missing required fields, invalid autonomy values, current version, migratable old version, unsupported future version, and an **old v0.14.0 CLI reading a newer roster file**. That last compatibility fixture must prove the old CLI refuses the newer schema rather than silently misreading fields added by a future release. No generated or listed output may be emitted after validation fails.

Cross-reference EF-28 in implementation and tests, but do not merge the work: EF-27 fixes the loader trust boundary; EF-28 fixes spell authorization and consent gates.

## Open questions

Should validation use a runtime schema library or local type guards, and how many historical schema versions must remain migratable? Agent definitions currently have no explicit schema-version field; should they gain one, or should their compatibility version be inherited from the roster/package contract?
