## Claim

Auto-merge is enabled on the condition "CI is green." Nothing in that condition connects to whether
a review round is still open on the same pull request. CI green means *the tests that exist pass* —
it says nothing about whether a review already in flight has found a blocker. When an adversarial
review round is running and auto-merge fires, the PR closes mid-round and any fix that had not yet
been pushed is stranded on a closed PR's branch.

This is not hypothetical. It fired once, and it shipped a HIGH defect to npm.

## Verification

Confirmed from the 2026-08-23 session record, not inferred:

- The operating decision was recorded as **D8** in that session's plan — *"auto-merge on green with a
  skip-and-continue"* ([journal/2026-08-23-docs-mode-push-safety-and-arc028.md:12](../../../journal/2026-08-23-docs-mode-push-safety-and-arc028.md)).
  D8 is a **plan-local label**, not a governance identifier, which is part of why the gap has been
  tracked nowhere since. It also collides with an unrelated `D8` in
  [spell-authoring-standards.md:87](../../../.arcane/governance/spell-authoring-standards.md) —
  "Conciseness & non-duplication" — so the label cannot be used as a durable reference.
- The firing is recorded at
  [journal/2026-08-23-docs-mode-push-safety-and-arc028.md:116-121](../../../journal/2026-08-23-docs-mode-push-safety-and-arc028.md):
  auto-merge fired on CI green for PR #63 while an adversarial round was still open. It merged the
  first fix commit; the second — the one fixing the HIGH finding — landed on a closed PR's branch and
  never reached `main`. **`0.20.0` went to npm with the defect live.**
- The journal classifies it as *"the one unaddressed process gap from the run."* The
  2026-08-23 session handoff raised it a second time, still unaddressed.
- **It is not covered by [ARC-024](../../../DECISIONS.md#arc-024--confirmed-severity-must-have-operational-consequences).**
  Checked against the implementation rather than the decision text: `src/modules/incident-gate.ts`
  gates on records in the incident queue that already carry a `severity` field. A finding raised
  inside an open review round is not yet a filed record, so the gate cannot see it. ARC-024 closes
  the *filed-but-ignored* path; this is the *found-but-not-yet-filed* path, and they do not overlap.

## Impact

Two independent failures compose, which is why the outcome was worse than either alone:

1. **A merge completes while a blocker is known but unrecorded.** The reviewer has the finding; the
   merge rule cannot see it.
2. **The stranded-commit mode is silent.** Merging a PR takes the commits pushed *at that moment*.
   Work pushed afterward targets a closed PR and reaches nothing. No error is raised, and the branch
   still looks like it contains the fix — because it does. `main` simply does not.

The second is what turned a process gap into a shipped defect, and it is also why "verify the merge,
not the merge report" became standing practice for the rest of that run. That practice is a
detection compensator; it does not prevent the merge from firing early.

Severity is `high` rather than `medium` because this already produced live consumer harm — a
published npm release carrying a known HIGH defect — rather than a latent risk.

## Proposed fix

Not routed straight to implementation: the decision is **what signal is authoritative for "a review
round is open,"** and it collides with existing shipped behaviour.

The ADR must settle:

- **Where the open-round signal comes from.** Options include a required review state on the
  provider, a draft/ready-for-review transition, a label applied for the duration of a round, or an
  explicit round-close comment. Each has a different failure mode when the reviewer is an agent
  rather than a human.
- **Whether auto-merge is narrowed or removed.** The skip-and-continue property D8 was chosen for is
  real and worth preserving for genuinely routine changes; a blanket removal trades one cost for
  another.
- **How the stranded-commit mode is made loud.** Whether or not the merge rule changes, pushing to a
  branch whose PR is already closed should not be silent. This is separately valuable and may be the
  cheaper half.
- **Interaction with the authorization gate** in `spell-create-pull-request`, which already
  distinguishes commit approval from merge approval for interactive Magus+. That gate governs whether
  *an agent* may request auto-merge; it says nothing about a repo-level auto-merge setting firing on
  its own.

## Open questions

1. Is the authoritative signal a provider primitive (review state, draft status) or an Arcane-owned
   convention? A provider primitive is enforceable but not portable across GitHub and ADO; an
   Arcane convention is portable but is prose unless something checks it.
2. Should the rule bind at merge time only, or should `spell-create-pull-request` refuse to enable
   auto-merge at all while a round is open?
3. Does this warrant amending ARC-024 to cover in-flight findings, or a new record? The mechanisms
   differ enough (queue gate vs. merge gate) that a new record is the current expectation, with a
   `Related:` link both ways.
4. Is the repo-level auto-merge setting currently on for this repository? The 2026-08-23 firing
   establishes it was on then; nothing since has recorded a change, and that should be confirmed
   from the platform rather than assumed either way.
