  - **Play's track model, stated up front — this is the single biggest source of wasted time.** *Internal testing* publishes with **no review**. *Closed*, *open*, and *production* each trigger review. Approval on one track does **not** promote the binary anywhere: production is a separate track needing its own release **and its own country list**. Batched clicks land on the wrong questions and can silently set things like graphic violence or location sharing to *Yes*. A dependency that is installed but no longer called still contributes its permissions, and every permission is a review and Data-safety surface. Removing one means removing the dependency, not just the call site — and the removal must be verified against the new binary.
  - **Android notification icons are a native concern with no iOS equivalent.** Android needs a dedicated **monochrome white-on-transparent small icon**; without one it falls back to a generic glyph. That is a native config change, so it ships in a **build, never an OTA**. Before diagnosing "the icon is broken", check the notification shade rather than the heads-up banner — OEM skins legitimately omit the small icon from banners. The branded slot is `largeIcon`.

Use a real bottom sheet dismissible three ways: cancel row, scrim tap, hardware back.

  **Cross-platform lessons that belong in the shared preamble (both stores):**
  - **Never ship a native rebuild while a submission is in review** just to carry a JS-only change — it can cost the queue position. Hold the change and ship it as an OTA after the verdict.
  - **A reviewer's FIRST cold launch must already be correct**, so a review build must carry the work natively rather than relying on an update being fetched. This is the direct consequence of the two-launch rule below.
  - **OTA updates apply on the NEXT launch, not the current one** — the client downloads in the background and swaps on relaunch. Do not diagnose a "stuck" update until two full quit-and-reopen cycles.
  - **🔴 Bundler transform caches do not key on `EXPO_PUBLIC_*` env vars.** On a persistent (self-hosted) runner the cache survives between runs, so an update published to one channel can ship another channel's inlined config — e.g. a production build pointing at the development API. Pass `--clear-cache` on the publish lane, and **verify by comparing the published `launchAsset` hashes across channels**: identical hashes for two channels that differ by at least one env var is proof of the defect. Pipeline-green is not evidence here.
  - **When a feature is removed or renamed, both stores' screenshots and descriptions are inside the blast radius.** Store metadata outlives the code it depicts and is the first thing a reviewer opens.

- [ ] **MEDIUM bug: merged-branch cleanup is ancestry-based, but ARC-009's own sanctioned merge strategies defeat ancestry checks — cleanup needs content-level verification and an idempotent sweep, not a merge-time trigger.** Field finding (2026-08-21): 18 stale local branches had accumulated in a consumer repo across ~2 weeks of sessions despite agent-policies' "After merge: the merging actor deletes the source branch (local and remote)". Three structural causes, none of them operator error:
  1. **The assigned actor doesn't exist at trigger time.** PRs complete in the host's web UI — often by the human, days after the authoring session ended. The host deletes the *remote* branch, but no web-UI merge can delete a branch inside a local clone that isn't running. Local pile-up is built into the "merging actor cleans up" model.
  2. **ARC-009 §7 sanctions Rebase-and-fast-forward, and a rebased branch never passes the prescribed cleanup checks.** git-conventions' cleanup steps (`git branch -d`, `git branch --merged`) and spell-open-session's stale-branch check are all ancestry-based; a rebase rewrites SHAs, so a branch merged via a fully sanctioned strategy is permanently invisible to `--merged` and refused by `-d`. Pre-ARC-009 squash merges leave the same signature. One sanctioned strategy structurally defeats the sanctioned cleanup commands.
  3. **Environment permission classifiers can deny cleanup commands mid-run** (`git push origin --delete`, `az repos pr update --status completed`) — the runbook step silently drops and nothing records that cleanup is still owed.

  Fixes, in dependency order: **(a)** Replace ancestry-based merged-detection in git-conventions' cleanup section and spell-open-session with content-level verification — `git cherry` / patch-id equivalence against the *freshly fetched* trunk (fetch first: a stale local trunk under-counts and produced a real false reading in the field), with commit-subject matching as the fallback where rebases rewrote patch-ids — then delete with `-D` only what passes, and treat a branch that *fails* verification as a finding to surface, not an obstacle. In the field test, content verification cleared 17 of 18 branches as landed and caught 1 genuinely unmerged branch that a naive `-D` sweep would have destroyed; the verification step is where the caution belongs, not in refusing to delete. **(b)** Add an idempotent verified-landed sweep to spell-close-session — open-session already *lists* stale branches, but nothing ever *prunes*, so accumulation is unbounded; a sweep converts "the merging actor deletes" from an obligation no actor can always fulfill into a step any session completes for all predecessors. When the environment denies a cleanup command, the spell must hand the operator the exact command to run rather than dropping the step silently. **(c)** Mechanical enforcement of the merge-strategy set — folded into the `doctor`/`ward` branch-policy item above. Done when: git-conventions' cleanup section and both session spells verify by content rather than ancestry, close-session carries the sweep, and doctor flags a repo whose host settings still permit squash.

- [ ] **`spell-full-cycle`: no cross-epic coordination for parallel/multi-epic runs against the same target repo.** Real dogfooding finding (a consumer repo, 2026-07-17): ran 4 epics as separate `spell-full-cycle` invocations (3 in parallel isolated worktrees, 1 sequential) against one target repo. Each epic's own Phase 3 "Implement" only ever sees its own isolated worktree, so nothing catches (a) two epics independently claiming the same DB-migration sequence number, or (b) two epics adding distinct imports to the same region of the same file — both surfaced only at human merge-review time.
