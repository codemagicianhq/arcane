  - **Play's track model, stated up front — this is the single biggest source of wasted time.** *Internal testing* publishes with **no review**. *Closed*, *open*, and *production* each trigger review. Approval on one track does **not** promote the binary anywhere: production is a separate track needing its own release **and its own country list**. An operator who watches a closed-test release go green will reasonably believe the app is live; it is not. Say this in the first paragraph of the Android section.

A spell that stops at "Save" ships nothing. Same trap on the listing pages, which use a separate "Save and publish" with its own second dialog.

  - **The IARC content-rating questionnaire re-renders when the app category changes**, shifting rows underneath answers already given. Batched clicks land on the wrong questions and can silently set things like graphic violence or location sharing to *Yes*. Answer one question at a time and re-read the form after any category change.
  - **Data safety hinges on one definition:** data is "collected" only if it leaves the device. On-device-only processing is not collection. The answers must also agree with the published iOS App Privacy responses, since both are public.
  - **Locale lists differ between the stores.** Release notes are per-language inside tags (`<locale-code>…</locale-code>`), and Play's catalogue does not match Apple's — a locale that exists on one store may not exist on the other, so the default-language choice has to be made against Play's own list rather than copied across.

  - **🔴 Signing: Play App Signing plus "automatic protection" can make the installed app present a signing certificate that appears on NO console page you would naturally look at.** Anything keyed to a `(package, SHA-1)` pair — Maps, Google Sign-In, App Links/`assetlinks.json` — then fails on Play-delivered installs while working perfectly on sideloads. **Never infer an Android SHA-1; read the cert the installed app actually presents from `adb logcat`.** Two corollaries that cost hours: zero traffic in a provider's usage metrics does *not* mean the app isn't calling (auth fails before any billable request is recorded), and a working browser-based OAuth flow proves nothing about certificates because it never checks them.

Removing one means removing the dependency, not just the call site — and the removal must be verified against the new binary.
  - **Android notification icons are a native concern with no iOS equivalent.** Android needs a dedicated **monochrome white-on-transparent small icon**; without one it falls back to a generic glyph. That is a native config change, so it ships in a **build, never an OTA**.   **Cross-platform lessons that belong in the shared preamble (both stores):**
  - **Never ship a native rebuild while a submission is in review** just to carry a JS-only change — it can cost the queue position. Hold the change and ship it as an OTA after the verdict.
  - **A reviewer's FIRST cold launch must already be correct**, so a review build must carry the work natively rather than relying on an update being fetched. This is the direct consequence of the two-launch rule below.
  - **OTA updates apply on the NEXT launch, not the current one** — the client downloads in the background and swaps on relaunch. Do not diagnose a "stuck" update until two full quit-and-reopen cycles.

Pipeline-green is not evidence here.
  - **When a feature is removed or renamed, both stores' screenshots and descriptions are inside the blast radius.** Store metadata outlives the code it depicts and is the first thing a reviewer opens.

- [ ] **`spell-full-cycle`: no cross-epic coordination for parallel/multi-epic runs against the same target repo.** Real dogfooding finding (a consumer repo, 2026-07-17): ran 4 epics as separate `spell-full-cycle` invocations (3 in parallel isolated worktrees, 1 sequential) against one target repo. Each epic's own Phase 3 "Implement" only ever sees its own isolated worktree, so nothing catches (a) two epics independently claiming the same DB-migration sequence number, or (b) two epics adding distinct imports to the same region of the same file — both surfaced only at human merge-review time. Worse: a migration's Phase 4 "Test" gate only ever runs against a fresh/empty test database, so a schema change that's wrong specifically against _real, pre-existing_ target data (a unique index that conflicted with legitimate duplicate rows the target app allows by design) passed every epic's own test run cleanly, then broke the consumer's actual deploy pipeline on the first live attempt — costing two extra pipeline cycles to properly root-cause, since the first fix wrongly assumed the broken migration had already applied somewhere (it never had, since the runner rolls back the whole transaction on failure and halts).
